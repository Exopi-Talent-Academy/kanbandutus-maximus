# Architecture Decision Records

## ADR-001: Use FastAPI as Backend Framework

### Status
Accepted

### Context
The project requires a REST API backend for a Kanban board application. The frontend will be built in Angular as a Single Page Application. We need a framework that provides automatic API documentation, input validation, and good performance.

### Decision
Use FastAPI as the backend web framework with Uvicorn as the ASGI server.

### Alternatives Considered
- **Flask**: Simpler but lacks automatic OpenAPI documentation and async support
- **Django**: Overkill for this use case, too opinionated
- **Express.js**: Would require a different language (JavaScript/TypeScript)

### Consequences
**Positive:**
- Automatic OpenAPI/Swagger documentation at `/docs`
- Pydantic for request/response validation
- Native async support for better performance
- Type hints integrate with documentation

**Negative:**
- Learning curve for team members unfamiliar with FastAPI
- More dependencies than a minimal framework

## ADR-002: JSON File Storage with Strategy Pattern

### Status
Accepted

### Context
The MVP requires simple data persistence without the complexity of database setup. The project may need to scale to a real database later.

### Decision
Implement storage using JSON files with a Strategy Pattern interface allowing future storage backends.

### Alternatives Considered
- **SQLite**: Requires DB setup, migrations, and ORM
- **PostgreSQL**: Overkill for MVP, requires running server
- **In-memory only**: Data lost on restart

### Consequences
**Positive:**
- Zero configuration and setup
- Human-readable data format for debugging
- Easy to swap implementations later

**Negative:**
- No ACID guarantees
- Concurrent access issues
- Performance degrades with large datasets
- No query capabilities beyond ID lookups

## ADR-003: No Authentication for MVP

### Status
Accepted

### Context
The MVP focuses on core Kanban functionality. Authentication adds significant complexity and is not required for initial development and testing.

### Decision
Skip authentication entirely for the initial release.

### Consequences
**Positive:**
- Faster development
- Simpler architecture
- Easier testing

**Negative:**
- Anyone can modify any data
- No user isolation
- Not suitable for production use

### Superseded By
This decision will be reconsidered when preparing for production deployment.

## ADR-004: RFC 7807 Error Format

### Status
Accepted

### Context
API errors should be machine-readable and provide sufficient information for debugging.

### Decision
Use RFC 7807 Problem Details for HTTP APIs error format.

### Format
```json
{
  "type": "https://api.example.com/errors/task-not-found",
  "title": "Task Not Found",
  "status": 404,
  "detail": "Task with id=999 not found"
}
```

### Consequences
**Positive:**
- Standardized error responses
- Machine-readable error types
- Consistent error structure

**Negative:**
- More verbose than simple error messages
- Requires client to parse structured errors

## ADR-005: Auto-integer ID Generation

### Status
Accepted

### Context
Entities need unique identifiers for API references.

### Decision
Use auto-incrementing integers for entity IDs, generated by finding the maximum existing ID.

### Consequences
**Positive:**
- Simple implementation
- URL-friendly IDs
- Easy to understand

**Negative:**
- Predictable IDs (security concern)
- Race conditions possible with concurrent creates
- Limited scalability (will need migration at high volumes)
